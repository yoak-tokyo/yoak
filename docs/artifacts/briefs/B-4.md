# B-4 指示書：workers.dev での公開に合わせる

決定ログ `docs/artifacts/decisions.md` の AD-13（と AD-4・AD-5・AD-8・AD-11）、`docs/artifacts/setup.md` を先に読む。

## 1. Access の JWT があれば Basic 認証をかけない（`worker/index.ts`）
- `/artifacts*`・`/api/artifacts*` 以外のパスで、`getAccessEmail()` が通る（Access の JWT が正しい）なら Basic 認証を飛ばす
- JWT が無い・不正なら今までどおり Basic 認証（`BASIC_AUTH_PASSWORD` があるとき）
- `/artifacts*`・`/api/artifacts*` の動きは変えない
- JWT の検証は1リクエストにつき1回だけにする（`/_next/*` などの静的ファイルにも毎回かかるので、無駄に2回検証しない）。jose の JWKS はすでに使い回している

## 2. 手順書を workers.dev 向けに直す（`docs/artifacts/setup.md`）
- 「Access Application を作る」を、Workers の画面から workers.dev とプレビュー URL に Access をかける手順にする（Workers & Pages → yoak-corporate-site → Settings → Domains & Routes → workers.dev / Preview URLs の Cloudflare Access を有効にする）。画面の名前は Cloudflare の公式ドキュメントで確かめる
- 有効にしたときに自動で作られる Access Application のポリシーを、AD-11 のとおり（Google だけ、Emails で1件ずつ）に直す手順
- `ACCESS_AUD` はその Application の AUD Tag、`ACCESS_TEAM_DOMAIN` は Zero Trust のチームドメイン
- コーポレートサイトのプレビューも同じログインの対象になることを書く
- yoak.tokyo のパス別 Application の手順は「将来 yoak.tokyo をこの Worker に向けるとき」の節に移して残す
- 確かめ方を workers.dev の URL で書き直す。workers.dev の正確な URL は PO から受け取る（README の `yoak-corporate-site.yoak-corporate-site.workers.dev` は今は名前解決できない）ので、`<workers.dev の URL>` と書いておく
