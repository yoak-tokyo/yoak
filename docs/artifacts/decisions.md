# アーティファクト共有 決定ログ

新しいものを下に足す。番号は `AD-<連番>`。

## AD-1 コーポレートサイトのリポジトリの中に作る（2026-10-13・PO）

別リポジトリにはせず、yoak リポジトリの `/artifacts` として作る。

## AD-2 アーティファクトは URL を登録する（2026-10-13・PO）

本体は claude.ai に置いたまま、リンクにタイトル・説明・分類などを付けて一覧にする。HTML のアップロードはしない。

## AD-3 見られるのは Google アカウントでログインした人と、許可した人（2026-10-13・PO）

基本は Google アカウントでログインする。許可した別のアカウントも見られるようにする。

## AD-4 認証は Cloudflare Access のパス別 Application、データは D1（2026-10-13・PM）

- `/artifacts*` と `/api/artifacts*` だけを Access で保護し、コーポレートサイトの公開ページには影響させない
- Worker 単位の Access（`ctx.access`）は Worker 全体が保護されるので使わない
- Worker で `Cf-Access-Jwt-Assertion` を jose で検証する（署名・aud・iss・期限）。workers.dev など Access を通らない経路は JWT が無いので 401
- 許可メールの人は Access の One-time PIN で入れる
- 保存先は Cloudflare D1

## AD-5 `/artifacts` 配下には Basic 認証をかけない（2026-10-13・PM）

プレビュー用の Basic 認証と Access の二重ログインを避けるため、`/artifacts*` と `/api/artifacts*` は Access の JWT 検証だけにする。

## AD-6 PR で lint・型チェック・build を回す CI を足す（2026-10-13・PM）

マージの条件にするため。

## AD-7 マージの判定は GitHub Actions の CI で行う（2026-10-13・PM）

Cloudflare の Workers Builds は、PR（main 以外のブランチ）では変更の中身に関係なく失敗している（#2〜#4 すべて。main ではデプロイが成功）。
原因はダッシュボードでしか見られないため PO に確認をお願いし（T-2）、それまでマージの判定には GitHub Actions の「lint・型チェック・build」を使う。

## AD-8 プレビュー環境での二重ログインは許す（2026-10-13・PM）

Basic 認証のパスワードがある環境（プレビュー）では、`/artifacts` は Access、ページが読む `/_next/*` は Basic 認証になり、2 回ログインすることになる。
yoak.tokyo の本番では Basic 認証を使わない前提なので、プレビューだけの不便として許し、仕組みは足さない。
なお 2026-10-13 時点で yoak.tokyo の DNS は Value-Domain、配信は Studio で、この Worker にはまだ向いていない（Q-4）。

## AD-9 リリース1 の機能（2026-10-13・PO、Q-1）

登録・一覧・キーワード検索・タグ絞り込み・編集と削除。編集・削除できるのは登録した本人だけ。サムネイルは後回し。お気に入り・通知・コメントは作らない。

## AD-10 分類は「事業を1つ（必須）＋自由なタグ」（2026-10-13・PO、Q-2）

事業は Yoak / nightbrew / nomitai / LAMP / CaseMatch / その他 から1つ必ず選ぶ。事業はタグとは別の項目として持つ（B-3）。

## AD-11 ログインは許可したメールアドレスの Google アカウントだけ（2026-10-13・PO、Q-3）

- Google ログインだけを使う。One-time PIN は使わない。Google 以外の人には Google アカウントを作ってもらう
- 許可するメールアドレスは PO が Cloudflare の Access のポリシーで1件ずつ足す。ドメイン単位では許可しない

## AD-12 画面は案B「インデックス」（2026-10-13・PO、UX-1）

- 表に近い行リスト。モックは `docs/artifacts/mocks/b-index.html`
- 詳細ページは作らず、一覧から claude.ai を直接開く。編集・削除の入口だけを用意する
- タグは自由入力で、よく使うタグを候補に出す
- 並びは新しい順で固定

## AD-13 workers.dev のアドレスで公開し、Worker 全体に Access をかける（2026-10-13・PO＋PM、Q-4）

- PO：社内で使うだけなので独自ドメインは要らない。コーポレートサイトの切り替え時期は未定
- PM：yoak.tokyo は Cloudflare に無いので、Worker の workers.dev（とプレビュー URL）に Cloudflare Access をかける。workers.dev の Access は Worker 単位なので、コーポレートサイトのプレビューも同じ Google ログインの対象になる
- Access の JWT が正しいリクエストには Basic 認証をかけない（二重ログインを避ける。AD-8 を置き換える）。JWT が無い経路では今までどおり Basic 認証
- 将来 yoak.tokyo をこの Worker に向けるときは、AD-4 のパス別 Application を足す（手順書に残す）

## AD-14 一覧の絞り込みはブラウザ側、画面の切り替えで URL は変えない（2026-10-13・PM、リリース1）

- 一覧は全件を取り、キーワード（スペースで AND）・事業・タグの絞り込みはブラウザ側で行う。社内の件数なら十分で、モックの動きに合う。件数が数百を超えたら API の `q`・`tag`・`business` に切り替える
- 一覧・登録・編集の切り替えで URL は変えない（モックと同じ）。ブラウザの「戻る」で一覧に戻したくなったら見直す

## AD-15 画面の仮置きの確認（2026-10-13・PO、UX-2）

- 編集・削除の入口、事業の入力、仮の文言は W-1 のまま
- 入力の上限はモックどおり（タイトル 60 字・説明 200 字・タグ 5 個）
- 登録者は名前で出したい → 取り方を R-1 で調べてから決める
- 追加の希望：URL を入れたらタイトル・説明・タグを推測して自動で入れたい → できるかを R-1 で調べてから決める

## AD-16 登録者は名前で出す。Google の名前を使い、取れなければ本人が入れる（2026-10-13・PO、Q-5）

- Google ログインの情報から名前が取れればそれを出す
- 取れなければ、本人に表示名を入れてもらう
- 名前が無い人（まだ登録していない人など）は、今までどおりメールの @ より前を出す

## AD-17 URL からの自動入力は作らない（2026-10-13・PO、Q-6）

R-1 のとおり URL だけからは中身を読めない。定型文や Claude での推測も作らず、よく使うタグの候補（実装済み）だけにする。

## AD-18 名前の持ち方（2026-10-13・PM、AD-16 の実装）

- D1 に `profiles`（メール → 名前、出どころ `google` / `self`）を持つ。一覧の登録者名はここから引く
- `GET /api/artifacts/me` で名前が無ければ、Worker が Access の `get-identity` を JWT 付きで 1 回呼び、name があれば `google` として保存する。取れなくてもエラーにしない
- 本人が入れた名前（`self`）は Google の名前で上書きしない
- Google で name が入るかは T-1 のあとに確かめる。入らなければ全員「本人が入力」になるだけで、作り直しは要らない
